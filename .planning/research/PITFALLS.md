# Domain Pitfalls

**Domain:** Time-series trend analytics on top of an existing SQLite time-tracking data model (TaskTimer — per-class study-time trends across weeks/months, streak visualization over time, time-of-day patterns)
**Researched:** 2026-09-20
**Overall confidence:** MEDIUM (cross-checked web sources on general timestamp/DST/streak/rollup pitfalls, HIGH-confidence for the codebase-specific findings below which are grounded directly in this repo's actual schema/migrations/queries, not general web claims)

## Grounding: How This Project Actually Stores and Buckets Time

Read directly from `src-tauri/src/db/migrations/0001_init.sql`, `0004_week_planning.sql`, `src-tauri/src/commands/analytics.rs`, and `src-tauri/src/timer/mod.rs` before writing the pitfalls below, so recommendations are specific to this codebase, not generic:

- `time_sessions.start_ts` / `end_ts` are `TEXT NOT NULL`, populated via SQLite's `datetime('now')` (see `timer/mod.rs:139,149,204,256`). SQLite's `datetime('now')` returns **UTC**, formatted `YYYY-MM-DD HH:MM:SS` with no timezone suffix — so the column is naive UTC text, not a tz-aware value.
- Every existing analytics query converts to local time at **query time** via the `'localtime'` modifier: `date(ts.start_ts, 'localtime')`, `strftime('%Y-%m', ts.start_ts, 'localtime')` (`commands/analytics.rs:195,205,215,229,253,368,436,479,747,765,861`). This is the correct "store UTC, localize at read" pattern — new trend queries **must** follow it, not introduce a second convention.
- Week start is **not** computed with `strftime('%W')` or `%U` anywhere in this codebase. `get_analytics_week` instead derives the Monday boundary manually: `date('now','localtime','-' || ((CAST(strftime('%w','now','localtime') AS INTEGER)+6)%7) || ' days')` (`analytics.rs:205`). `%w` returns 0=Sunday..6=Saturday; `(%w+6)%7` remaps it to 0=Monday..6=Sunday, then subtracts that many days to land on Monday.
- Streaks (`current_streak`, `longest_streak`, `analytics.rs:824-859`) are computed in **Rust**, not SQL, over a `BTreeSet<NaiveDate>` built from `SELECT DISTINCT date(ts.start_ts,'localtime')` (`tracked_days()`, `analytics.rs:861`). `current_streak` anchors on `chrono::Local::now().date_naive()` and has an explicit "hasn't studied yet today doesn't break the streak" rule (see the doc-comment at `analytics.rs:824-827`) — this exact semantic must be preserved by any new streak-over-time / streak-history feature, not re-derived from scratch in SQL.
- `time_sessions` has a **plain** index `idx_time_sessions_start_ts ON time_sessions(start_ts)` (`0004_week_planning.sql:9`) and `idx_time_sessions_task_id` (`0001_init.sql:47`). There is **no expression index** on `date(start_ts,'localtime')` or `strftime('%Y-%m', start_ts,'localtime')` anywhere in the migrations.
- `rusqlite` is pulled in with `features = ["bundled"]` only (`Cargo.toml:31`) — the `series` (generate_series virtual table) feature is **not** enabled, so `generate_series()` is not available for gap-filling calendar buckets.
- `CONCERNS.md` already flags "Analytics Queries Not Indexed" as a performance bottleneck — that claim is half-true (a plain `start_ts` index exists) but the real problem, confirmed by reading the queries, is more precise than the existing writeup: see Critical Pitfall 1 below.

## Critical Pitfalls

### Pitfall 1: Function-Wrapped Column Predicates Silently Defeat the Existing `start_ts` Index
**What goes wrong:** Every existing (and any naively-written new) trend query filters/groups with `date(ts.start_ts, 'localtime') = ...` or `strftime('%Y-%m', ts.start_ts, 'localtime') = ...`. Wrapping an indexed column in a function makes the predicate non-sargable — SQLite cannot use `idx_time_sessions_start_ts` to seek, so it falls back to a full table scan of `time_sessions` for every analytics call, evaluating `date(...)`/`strftime(...)` on every row.
**Why it happens:** The plain `CREATE INDEX ... (start_ts)` (`0004_week_planning.sql:9`) indexes the raw TEXT value, not the localized/derived value the WHERE clause actually filters on. SQLite does not automatically infer that `date(start_ts,'localtime') = date('now','localtime')` could be satisfied by a range scan on `start_ts` itself, because timezone conversion isn't monotonic-safe from SQL's point of view without an explicit expression index.
**Consequences:** Fine today (small personal dataset), but a longitudinal trends feature is exactly the workload that multiplies this cost — instead of one "this week" query, a trends view will fire 12+ month buckets, N weeks of history, and per-class breakdowns, each doing its own full scan. Over years of daily use this becomes the first real slowdown the user will notice, and it will look like "the app got slow" with no obvious cause since `EXPLAIN QUERY PLAN` still shows an index that "exists."
**Prevention:** Either (a) add SQLite expression indexes matching the exact bucketing expressions used, e.g. `CREATE INDEX idx_time_sessions_local_date ON time_sessions(date(start_ts,'localtime'))`, or (b) denormalize: add a generated/maintained `local_date TEXT` (and optionally `local_year_month TEXT`) column populated at insert/update time, indexed normally, and have all bucketing queries filter on that column instead of wrapping `start_ts` in a function per-query. Prefer (b) for this codebase since sessions are also edited (`edited` flag, pause adjustments) — a stored column is easier to reason about and reuse across the new trend commands than N separate expression indexes.
**Detection:** Run `EXPLAIN QUERY PLAN` on the new trend queries; any `SCAN time_sessions` (not `SEARCH ... USING INDEX`) on a query that filters/groups by date confirms this pitfall is active.

### Pitfall 2: New Week-Bucketing Code Reinvents `%W`/`%U` Instead of Reusing the Existing Monday-Anchor Formula
**What goes wrong:** SQLite's `strftime('%W', ...)` counts Mondays from January 1st of the calendar year with no ISO "Thursday rule" or year-voting, and `%U` anchors on Sunday instead — both disagree with true ISO-8601 weeks, and neither matches this codebase's existing week definition. If a new "weekly trend over N weeks" query is written using `%W`/`%U` (the obvious first instinct when you need a "week bucket" and don't check existing code), its bucket boundaries will not agree with `get_analytics_week`'s Monday-start "this week," producing a trend chart whose last bar doesn't match the "this week" summary card, or a chart where week boundaries jump around at year-end.
**Why it happens:** `%W`/`%U` look like the "obvious" SQLite tool for "get me the week," but SQLite's own docs and forum explicitly warn `%W` is not ISO week numbering, and `%V` (true ISO week) requires a `%G` (ISO week-year) pairing to avoid ambiguity at year boundaries — and isn't guaranteed present in all SQLite builds.
**Consequences:** Off-by-one-week bars in the trend chart, worst right at semester boundaries (year-end/New Year) — exactly when a student's schedule (finals, winter break) makes the week-over-week comparison most visible and most likely to be scrutinized.
**Prevention:** Reuse the existing Monday-anchor arithmetic pattern from `get_analytics_week` (`(strftime('%w', start_ts,'localtime')+6)%7` day-of-week remap, then subtract to Monday) as the single source of truth for "which week does this session belong to," rather than `%W`/`%U`/`%V`. Extract it into one shared SQL fragment or Rust helper so the single-week card and the multi-week trend query can never drift apart.
**Detection:** Compare the last bucket of any new "N weeks" trend query against `get_analytics_week`'s existing result for the same period; a mismatch means two different week-boundary definitions are in play.

### Pitfall 3: Empty Weeks/Months/Days Are Silently Omitted, Not Shown as Zero
**What goes wrong:** `GROUP BY` only emits rows for buckets that have at least one session. A student who takes a week off (exam break, illness) will produce a trend query result that simply skips that week rather than returning a zero-value row for it — which, rendered directly into a line/bar chart, collapses two adjacent weeks together instead of showing a visible gap/dip to zero.
**Why it happens:** SQL aggregation is a table-shape operation; without an explicit calendar spine to `LEFT JOIN` against, there is no row to represent "this bucket, zero activity." This project does not have `generate_series()` available (rusqlite is built with `features = ["bundled"]` only, no `series` feature — `Cargo.toml:31`), so the common SQLite trick of `LEFT JOIN (SELECT value FROM generate_series(...))` is **not** available out of the box.
**Consequences:** Streak/trend charts that look continuous when the underlying data has real gaps — directly undermines the point of a "streak visualization over time" feature, which exists specifically to make gaps visible.
**Prevention:** Generate the full calendar bucket list (list of Mondays, list of `YYYY-MM`, list of dates) in Rust with `chrono` iteration (the project already depends on `chrono` throughout `analytics.rs`/`timer/mod.rs`), then `LEFT JOIN`/merge the SQL aggregate results onto that spine and default missing buckets to zero — mirroring how `current_streak`/`longest_streak` already build a `BTreeSet<NaiveDate>` and walk it day-by-day in Rust rather than trying to do gap-detection in pure SQL. Alternatively, if `generate_series` is wanted, it requires either enabling SQLite's `series` extension in rusqlite or a recursive CTE (`WITH RECURSIVE`) date spine — feasible, but adds SQL complexity this codebase doesn't currently have anywhere else.
**Detection:** Manually create a multi-week gap in test data (skip a week entirely) and verify the trend endpoint returns an explicit zero-value entry for that week, not a skipped index.

### Pitfall 4: Local-Time Bucketing Is Recomputed Against the *Current* System Timezone on Every Read, Not Frozen at Record Time
**What goes wrong:** Because `start_ts` is stored as naive UTC and every query applies `'localtime'` fresh at query time, the "local day" a session belongs to is a function of the *current* OS timezone setting, not the timezone that was active when the session actually happened. If the user's system timezone changes (laptop travel across zones, or a manual clock/timezone fix), historical sessions can retroactively shift which local calendar day — and therefore which streak day / week bucket / month bucket — they land in.
**Why it happens:** SQLite's `localtime` modifier always uses the OS's current timezone; there's no per-row stored offset. This is a single-user desktop app (per `PROJECT.md`), so this is a lower-probability event than in a multi-user/server context, but it's not zero — a student traveling home for break, or a laptop with a misconfigured/auto-corrected system clock, is a realistic scenario.
**Consequences:** A streak or trend chart that "changes history" after a timezone change — confusing and hard to debug because the underlying UTC data never changed, only the read-time interpretation did. This is a *moderate*, not critical, pitfall for this specific app given its single-user desktop nature, but it's exactly the kind of bug that's invisible in testing (dev machine timezone rarely changes) and only surfaces for the real user months later.
**Prevention:** Given this is a single-user local desktop app (not a sync-across-timezones product), the pragmatic fix is smaller than the general "store an explicit local_date column at insert time" advice from the wider ecosystem research — but it's still worth doing for Pitfall 1's sake anyway (denormalized `local_date` column populated once at session-end time, using the timezone active *then*), which as a side effect also fixes this pitfall for free. Do not "fix" this by trying to convert historical UTC timestamps using today's timezone offset after the fact.
**Detection:** Change system timezone, reopen the app, confirm existing streak/day totals for past sessions are unchanged from before the timezone switch.

## Moderate Pitfalls

### Pitfall 1: DST Transitions Distort Time-of-Day ("when do you actually study") Buckets
**What goes wrong:** The new "time-of-day patterns" feature will bucket sessions by hour-of-day in local time (`strftime('%H', start_ts, 'localtime')` or similar). Twice a year, DST transitions make this non-uniform: the spring-forward hour (2:00-3:00 AM local) doesn't exist, so any session logically "in" that window is pulled into an adjacent hour; the fall-back hour (1:00-2:00 AM local) occurs twice, so two real hours of wall-clock-distinct sessions collapse into one bucket, producing an artificial spike.
**Prevention:** For a student-facing "when do you study" chart, this is a minor visual artifact (study sessions are rare at 2 AM, and it self-corrects every 6 months), so full DST-aware bucketing is likely overkill — but the failure mode should be a known, accepted tradeoff rather than a surprise. If precision matters later, bucket on the UTC hour and only convert the *label* to local time for display, rather than grouping by a local-time-derived hour string.

### Pitfall 2: Streak-History / Longest-Streak-Per-Class Recomputes Full History On Every Request
**What goes wrong:** `tracked_days()` (`analytics.rs:861`) runs `SELECT DISTINCT date(ts.start_ts,'localtime') FROM time_sessions ...` with **no date range filter**, scanning the entire session history every call; `get_streaks` then calls it once per class plus once globally. `longest_streak()` similarly walks the full `BTreeSet` from scratch. A "streak visualization over time" feature that shows, say, a calendar-heatmap or streak-history-over-months view will likely call these (or similar unbounded queries) on every navigation, and doing so per-class multiplies the cost.
**Prevention:** Cap queries feeding any new trend/streak-history view to the relevant date range (e.g., last 12 months) rather than `SELECT DISTINCT` over all time; if full-history "longest streak ever" is still needed, keep that as a separate, deliberately-unbounded query rather than baking it into the same code path the trend view calls repeatedly. This does not require a materialized rollup table yet at this app's scale (single user, desktop, years not yet accumulated) — that's a "later" concern per the rollup pattern in the Minor Pitfalls section — but bounding the WHERE clause on new queries now avoids setting the same unbounded-scan precedent for a feature explicitly about "over time."

### Pitfall 3: `datetime('now')` in Test Fixtures vs. Bare Date Strings Creates Format Drift Risk
**What goes wrong:** Production code always inserts `start_ts`/`end_ts` via `datetime('now')` (full `YYYY-MM-DD HH:MM:SS`), but several test fixtures insert bare 10-character date strings like `'2026-09-15'` directly (`db/mod.rs:126,189`). Elsewhere in this codebase (the `due_expr`/`DURATION_EXPR` helper at `analytics.rs:154-157`) there's already a `CASE WHEN length(column)=10 THEN date(column) ELSE date(column,'localtime') END` pattern specifically to handle this exact ambiguity for other date columns — but the session-bucketing queries (`date(ts.start_ts,'localtime')`) do **not** apply that same normalization to `start_ts`/`end_ts`.
**Prevention:** If any new trend query reuses `start_ts`/`end_ts` in a new SQL fragment, either only test against realistic (full-datetime) fixtures, or apply the same length-based CASE normalization already established elsewhere in the file for consistency — don't assume `start_ts` is always a full datetime string just because production code currently guarantees it; a future CSV import or backfill path could introduce date-only values the same way `due_at`/`completed_at` apparently can.

## Minor Pitfalls

### Pitfall 1: Materializing Rollups Too Early Adds Complexity This App Doesn't Need Yet
**What goes wrong:** The general time-series ecosystem wisdom is "precompute rollup tables for historical periods, compute on-the-fly only for the recent open window, use multiple granularities." Applying that pattern here now (before there's a performance problem) means building and maintaining rollup tables, incremental upsert logic, and staleness invalidation — for a single-user SQLite file that, even after years of daily student use, will likely stay in the tens-of-thousands-of-rows range for `time_sessions`.
**Prevention:** Fix Pitfall 1 (Critical) — the missing expression index / denormalized `local_date` column — first; that alone should keep on-the-fly aggregation fast at this app's realistic scale. Only reach for materialized rollup tables if profiling (`EXPLAIN QUERY PLAN`, wall-clock timing on a multi-year synthetic dataset) actually shows the indexed on-the-fly queries are too slow.

### Pitfall 2: Recursive CTEs for Streak/Gap Detection Are Unnecessary Here
**What goes wrong:** The general "gaps and islands" SQL pattern (window functions or recursive CTEs) is the standard ecosystem solution for streak detection, and it would be tempting to reach for it when building "streak visualization over time." But this codebase already solves single-point-in-time streaks in Rust with a `BTreeSet<NaiveDate>` walk, which is simpler, already tested (`analytics.rs:917-958`), and already encodes the project's specific streak semantics (today-not-yet-studied doesn't break the streak).
**Prevention:** For a streak-*history* view (streak length at each point in time, not just "today's" streak), extend the existing Rust walk (iterate the `BTreeSet<NaiveDate>` and compute streak length as of each day) rather than introducing a parallel SQL-side gaps-and-islands query — two implementations of "what counts as a streak" is a correctness risk (they will eventually disagree at an edge case) more than a performance one at this scale.

| Phase Topic | Likely Pitfall | Mitigation |
